# Mistakes log

Newest entry first. One entry per mistake.

## 2026-08-29 — `localStorage` had been silently full for an unknown period, likely months, before anyone noticed

What happened: the owner's real, long-running install had `rpc-undo-stack` at 44 MB and `rpc-cloud-sync-lab-fp-index` at 8 MB — together already past what a browser origin's `localStorage` quota normally allows. Every `localStorage.setItem` call from that point on failed with `QuotaExceededError`, and every one of them was wrapped in a `try { ... } catch { }` that swallowed the error with no log, so nothing ever surfaced this: not a crash, not a console line, not a toast. The owner only discovered it because one unrelated feature (hiding a table column) happened to depend on a write to that same storage and visibly did nothing.
Root cause: `pushUndoSnapshot` in `public/js/features/productivity.mjs` deep-copies the entire clinical state (every patient, note, indicación, lab history entry, med receta, and the med catalog) into `localStorage` on every undo-able action, uncapped by size, only capped by count (5 entries). The codebase already has a real quota-pressure system built for exactly this class of problem — `public/js/storage-quota.mjs`, with `assessStoragePressure`/`estimateRpcPersistBytes`, wired into the main clinical persistence path in `public/js/storage/storage-save-all.mjs` — but the undo-stack writer never used it, so quota pressure from undo snapshots was invisible to that system. Meanwhile the swallowed `catch` blocks meant no individual write failure was ever visible either. Two independent silences stacked on top of each other, so the failure could grow for as long as the app kept being used without anyone hitting a feature that made it visible.
Prevention: `saveUndoStack` now shrinks (drops oldest snapshots, then clears the key entirely) instead of failing, and logs a `console.warn` every time it has to do that, so quota pressure on this key is visible again the next time it happens. `tend-prefs.mjs`'s write path now logs instead of swallowing too. The general rule going forward: a `catch` around any storage write must at least log — an empty `catch {}` on a write is how a real failure becomes invisible for months. Did not audit the other ~115 `localStorage.setItem` call sites in this codebase for the same pattern — that is a separate, larger task, out of scope for this fix.

## 2026-08-29 — shipped a `.wb-scrim` overlay fix for the table-hide bug that was not the actual cause

What happened: after a senior-dev escalation pointed at a plausible-but-unconfirmed overlay leak (`.wb-scrim` missing `pointer-events: none` when closed), I shipped that fix and told the owner it was solved. It was not — the owner tried again and the checkbox still did nothing. The real cause only surfaced because a second fix (stop swallowing the `localStorage.setItem` error in `tend-prefs.mjs`) turned a previously-silent failure into a visible `QuotaExceededError` in the console.
Root cause: `pushUndoSnapshot` in `public/js/features/productivity.mjs` stores a full deep copy of the entire clinical state (all patients, notes, indicaciones, lab history, med receta, settings, med catalog) into `localStorage` on every undo-able action, keeping up to 5 such snapshots with no size limit. For this owner's real census, `rpc-undo-stack` alone had grown to 44 MB, blowing past the browser's per-origin storage quota and silently failing every `localStorage` write app-wide, including the table-hide feature that had nothing to do with undo.
Prevention: When a fix is built on a plausible-but-unverified theory (found by code reading alone, no live repro), say so explicitly and ask the owner to confirm it worked before treating the bug as closed — do not present a guess as a fix. Any snapshot/undo mechanism that copies application state must cap the copy's byte size, not just the count of entries. Any `catch` around a storage write must at minimum log the error (not swallow it silently) — that single change is what actually surfaced this root cause.

## 2026-08-29 — told owner "just restart the app" for a click-does-nothing bug, and every verify script tested a click that can't fail

What happened: Owner reported the Tendencias table hide checkboxes did nothing on click. I told them to quit and restart the app, guessing stale bundle, without checking the DOM first. Restart did not fix it. Real root cause (found only after live DevTools debugging plus a senior-dev escalation): `.wb-scrim` (`public/styles/workbench-kit.css`), a full-viewport `position: fixed` overlay used by confirm dialogs, had no `pointer-events: none` when closed, so a leaked/leftover instance sat on top of everything and silently ate every click app-wide — real clicks and right-clicks both, while `element.click()` kept "working" since it bypasses hit-testing. Separately, `writeJson()` in `tend-prefs.mjs` swallowed any `localStorage.setItem` failure with an empty `catch`, so a write failure (e.g. quota) would also look exactly like "click does nothing," with no console error.
Root cause: (1) diagnosed from a guess (stale bundle) instead of checking the DOM/console first; (2) every existing verify script for this feature (`tend-group-table-hide.mjs`, `tend-group-table-hide-narrow.mjs`) used `inp.click()` or `elementFromPoint(...).click()` — a JS-level dispatch that skips hit-testing, `pointer-events`, and z-order entirely — so they always passed even while the real click path was broken by an overlay.
Prevention: For a "click does nothing" report, get live DOM/console evidence (DevTools, or a real click via `page.mouse.click`) before guessing a cause or suggesting a restart. Any verify script that claims to test "does a click work" must use `page.mouse.click(x, y)` (a real pointer event), never `.click()` on a JS reference — that only proves the listener is wired, not that a real click can reach it. Any full-viewport `position: fixed` overlay must ship with `pointer-events: none` in its closed/default state, re-enabled only in its `--open` state, so a leaked instance can't block the rest of the app.

## 2026-08-29 — table hide “fixed” with pointer-events on the wrapper only; tag chips still stole clicks

What happened: Owner still could not hide Tendencias table columns that had event tags (`1 CE`, `Plaq`, …) after a prior fix that set `pointer-events: none` on `.tend-event-col-tags`. Claimed fixed; it was not.
Root cause: In CSS, `pointer-events: none` on a parent does **not** disable descendants that keep the default `auto`. The red tag chips kept receiving the click, so the date checkbox never toggled.
Prevention: When blocking clicks through a decorative overlay, set `pointer-events: none` on the overlay **and its descendants** (`… *`), or turn the parent off and explicitly re-enable only the real control. Do not report click-through fixed without that descendant rule.

## 2026-08-24 — clinical read model never re-synced after boot on Electron, so bulk copy silently served stale data

What happened: user reported the team-wide Cmd+Shift+C copy (labs, and separately Estado actual) sometimes copied a previous day's data instead of the latest — even right after entering fresh labs or Estado actual notes. Root cause turned out to be architectural, not a formatting or sorting bug (my first hypothesis, ruled out once the user confirmed Estado actual copy had the same symptom, since that code path never touches lab date-sorting logic at all).
Root cause: `clinical-read-model.mjs`'s in-memory `_cache` (the store `getPatients()`/`getLabHistory()` read from, used by both bulk-copy functions and the sidebar) is only populated once at app boot (`app-state.mjs` → `hydrateClinicalRepoIntoReadModel`). Every save on Electron goes through `clinical-repo-persist.mjs`'s `runPersistNow`, which calls `executeClinicalCommand(..., { echoSnapshot: false })` — deliberately skipping the server-echoed snapshot to avoid a stale round-trip clobbering fresher local edits. But nothing else ever re-applied the local snapshot to `_cache` after that, so `_cache` stayed frozen at boot-time data forever, while the actual UI (which reads a separate legacy `app-state.mjs` array) kept showing correct, live data — masking the staleness everywhere except in code paths that specifically read from `clinical-read-model.mjs`.
Prevention: when two different in-memory stores exist for the "same" data (legacy array vs. read-model cache), grep every write path for both before trusting that "the UI looks right" means the data is fresh everywhere — a read-model that's fed only at boot is a silent trap for any feature added later that reads from it. Fixed by applying the already-known-correct local snapshot to `_cache` after persist succeeds (`_applyRepoSnapshot(snapshot, ...)` in `clinical-repo-persist.mjs`), without touching the deliberate `echoSnapshot: false` IPC behavior.

## 2026-08-18 — ran a 10-phase, ~100-file UI redesign to "done" on unit tests alone, never opened the app

What happened: Delegated a full-app redesign (12 phases) to a chain of lead-dev subagents to match a design handoff 1:1. Every phase reported "Done," build clean, tests passing. I passed all of that straight to the user as "matches the design 1:1." The user then ran the actual app, put it next to the mockup, and found six of the screens did not match at all: Laboratorio still rendered as the old flat text blob (only trend arrows were added, not the mockup's card/table layout); the "Texto de egreso" feature was untouched inline paragraphs instead of the mockup's compact modal; Nota de evolución still showed the legacy blank SOAP template because the new derived-Objetivo screen (built in Phase 8) was wired in as a secondary hidden button instead of replacing the primary tab; Pendientes kept the old checkbox-list UI with only grouping added, not the mockup's PRIOR/PENDIENTE/QUIÉN/VENCE table; and the calendar-popover component built in Phase 3 was never wired to any real screen — Phase 3's own report said so explicitly ("not yet wired to a live screen"), and I read that line and did not send anyone back to fix it.
Root cause: I treated "colocated unit tests pass + build is clean + the subagent says Done" as proof of visual fidelity. It is not — those checks verify HTML strings and CSS class names, not what renders on screen. I have Browser/simulator tools available in this session and never used them to open the app and screenshot it next to the mockup before telling the user it was done. I also read at least one subagent report that flagged unfinished wiring (the popover) and let it pass without following up. This is the same failure as the 2026-08-17 entries below, at 10x the scale: verifying a mockup match without diffing against the mockup itself.
Prevention: For any "match this reference 1:1" task, no phase/screen is done until a screenshot of the actual running app is taken and compared directly against the reference — by me, in this session, not inferred from a subagent's self-report or from "it uses the right CSS variables so it must be right." When a subagent's own report names something as unfinished or not-yet-wired ("small follow-up," "not yet connected to a live screen"), that is not closeable — it must be scheduled as its own explicit follow-up step before the parent task is called done. At orchestration scale (many subagents, many files), the temptation to trust aggregated "all tests pass" summaries instead of looking is exactly when this fails hardest — the more phases running unattended, the more important the actual visual check becomes, not less.

## 2026-08-18 — verify-tool's text-locator helper clicked a hidden element, read as a product bug

What happened: While verifying the DEMO PÉREZ fixture fix, `scripts/verify/goto-demo.mjs`'s `clickTopTab(page, 'Laboratorio')` (selector: `.tab:has-text("Laboratorio"), button:has-text("Laboratorio")`) silently matched a hidden same-text element elsewhere on the page instead of the real top tab (`#apptab-lab`), and the screen stayed on "Paciente" with an empty pane. For a few iterations that looked like a real rendering regression before I checked the DOM directly and found the click never landed on the intended element.
Root cause: `:has-text()` with no scoping matches the first DOM-order element containing that text anywhere on the page, not the visually-obvious one — a settings-dropdown entry or similar can share label text with the actual navigation tab and win the match.
Prevention: When a verify-tool screenshot looks wrong, check whether the intended UI state actually changed (dump DOM/URL/active-tab state) before concluding the app is broken. For this app's own tab/screen navigation, prefer `page.evaluate(() => document.getElementById('apptab-lab')?.click())` against real DOM ids from `public/partials/layout/app-body.html` over the text-locator helpers.
