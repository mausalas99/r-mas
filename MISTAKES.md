## 2026-09-17 — two sessions debugged the fold/merge code for the iPad→desktop sync bug; the real failure was one layer earlier, at decrypt

What happened: after the team-assign push bug (below) was fixed, the owner reported a new, reverse-direction bug: vitals edits and new patient registrations made on the iPad never reached the desktop. Live console instrumentation on the pull/apply path showed the op arriving correctly (`opsLen: 1`, right patient id, right path) but the merge producing `added: 0, updated: 0` — a real signal, but I read it as "the fold/merge logic must be dropping it" and kept tracing `pull-apply-state.mjs`/`patient-entries.mjs`/`mergeMonitoreo` deeper without finding the actual defect. After the owner said "too many tries," a CEO (Fable) review of the same evidence found it in one pass: the value reaching the merge still had no readable payload because it was an unopened E2EE ciphertext envelope (`{ enc: 1, iv, ct }`) — the desktop's turn-room connect path never called `loadRoomDek`, so a non-owner desktop never learns the room's key and `maybeDecrypt` silently returns ciphertext as-is with no error. A second, unrelated bug (the iPad's own mutation gate rejecting `entries/<pid>/fields`) explained the new-registration half of the same report and was 100% certain from code alone — it should have been caught by tracing what the iPad even attempts to send, before spending any time on the desktop's apply side.
Root cause: `added: 0, updated: 0` on a correctly-shaped op is consistent with several layers failing (fold, scope filter, merge no-op, *or* decrypt) and I picked the layer closest to where I'd been looking (fold/merge, same area as the earlier resolved bug) instead of checking the layer between "op received" and "op enters the merge" — decryption — which sits one function call earlier in the same file (`api-client.mjs`'s `pull` → `decryptOpsFromPull`) and is easy to skip past because a failed decrypt returns the ciphertext object unchanged rather than throwing.
Prevention: when a pulled op silently no-ops downstream, check decrypt status *before* tracing merge logic — log `!!getCachedRoomDek(roomId)` and whether the op's value still has `enc === 1` at the point it enters the fold. A value that "arrived" over the wire is not the same as a value that decrypted; E2EE means a payload can be present, correctly shaped, and still be opaque garbage to this specific device. Also: when two rounds of a fix attempt fail on the same report, that is itself a strong signal to get a second read on the same evidence rather than continuing to narrow within the same theory.
