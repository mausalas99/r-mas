## 2026-09-02 — rewrote the `test` script and never ran it; it could not start

What happened: the codebase-reduction session replaced the 31 KB test manifest with directory arguments (`--test lib public scripts …`) and reported "glob test discovery" done. Under Electron's Node 24, `--test lib` fails with `Cannot find module …/lib` — the whole suite was unrunnable. Found by the next session running `npm run test:one -- lib`.
Root cause: Node's test runner accepts glob patterns, not bare directories. The new script was never executed; only `test:one` on single files was.
Prevention: after any change to `scripts.test`, run the full command once and compare the reported test count with the previous run. Directory scope goes in as a quoted glob (`"lib/**/*.test.*js"`).

## 2026-08-29 — `localStorage` had been silently full for an unknown period, likely months, before anyone noticed

What happened: the owner's real, long-running install had `rpc-undo-stack` at 44 MB and `rpc-cloud-sync-lab-fp-index` at 8 MB — together already past what a browser origin's `localStorage` quota normally allows. Every `localStorage.setItem` call from that point on failed with `QuotaExceededError`, and every one of them was wrapped in a `try { ... } catch { }` that swallowed the error with no log, so nothing ever surfaced this: not a crash, not a console line, not a toast. The owner only discovered it because one unrelated feature (hiding a table column) happened to depend on a write to that same storage and visibly did nothing.
Root cause: `pushUndoSnapshot` in `public/js/features/productivity.mjs` deep-copies the entire clinical state (every patient, note, indicación, lab history entry, med receta, and the med catalog) into `localStorage` on every undo-able action, uncapped by size, only capped by count (5 entries). The codebase already has a real quota-pressure system built for exactly this class of problem — `public/js/storage-quota.mjs`, with `assessStoragePressure`/`estimateRpcPersistBytes`, wired into the main clinical persistence path in `public/js/storage/storage-save-all.mjs` — but the undo-stack writer never used it, so quota pressure from undo snapshots was invisible to that system. Meanwhile the swallowed `catch` blocks meant no individual write failure was ever visible either. Two independent silences stacked on top of each other, so the failure could grow for as long as the app kept being used without anyone hitting a feature that made it visible.
Prevention: `saveUndoStack` now shrinks (drops oldest snapshots, then clears the key entirely) instead of failing, and logs a `console.warn` every time it has to do that, so quota pressure on this key is visible again the next time it happens. `tend-prefs.mjs`'s write path now logs instead of swallowing too. The general rule going forward: a `catch` around any storage write must at least log — an empty `catch {}` on a write is how a real failure becomes invisible for months. Did not audit the other ~115 `localStorage.setItem` call sites in this codebase for the same pattern — that is a separate, larger task, out of scope for this fix.

## 2026-08-29 — told owner "just restart the app" for a click-does-nothing bug, and every verify script tested a click that can't fail

What happened: Owner reported the Tendencias table hide checkboxes did nothing on click. I told them to quit and restart the app, guessing stale bundle, without checking the DOM first. Restart did not fix it. Real root cause (found only after live DevTools debugging plus a senior-dev escalation): `.wb-scrim` (`public/styles/workbench-kit.css`), a full-viewport `position: fixed` overlay used by confirm dialogs, had no `pointer-events: none` when closed, so a leaked/leftover instance sat on top of everything and silently ate every click app-wide — real clicks and right-clicks both, while `element.click()` kept "working" since it bypasses hit-testing. Separately, `writeJson()` in `tend-prefs.mjs` swallowed any `localStorage.setItem` failure with an empty `catch`, so a write failure (e.g. quota) would also look exactly like "click does nothing," with no console error.
Root cause: (1) diagnosed from a guess (stale bundle) instead of checking the DOM/console first; (2) every existing verify script for this feature (`tend-group-table-hide.mjs`, `tend-group-table-hide-narrow.mjs`) used `inp.click()` or `elementFromPoint(...).click()` — a JS-level dispatch that skips hit-testing, `pointer-events`, and z-order entirely — so they always passed even while the real click path was broken by an overlay.
Prevention: For a "click does nothing" report, get live DOM/console evidence (DevTools, or a real click via `page.mouse.click`) before guessing a cause or suggesting a restart. Any verify script that claims to test "does a click work" must use `page.mouse.click(x, y)` (a real pointer event), never `.click()` on a JS reference — that only proves the listener is wired, not that a real click can reach it. Any full-viewport `position: fixed` overlay must ship with `pointer-events: none` in its closed/default state, re-enabled only in its `--open` state, so a leaked instance can't block the rest of the app.

## 2026-08-29 — table hide “fixed” with pointer-events on the wrapper only; tag chips still stole clicks

## 2026-08-24 — clinical read model never re-synced after boot on Electron, so bulk copy silently served stale data

What happened: user reported the team-wide Cmd+Shift+C copy (labs, and separately Estado actual) sometimes copied a previous day's data instead of the latest — even right after entering fresh labs or Estado actual notes. Root cause turned out to be architectural, not a formatting or sorting bug (my first hypothesis, ruled out once the user confirmed Estado actual copy had the same symptom, since that code path never touches lab date-sorting logic at all).
Root cause: `clinical-read-model.mjs`'s in-memory `_cache` (the store `getPatients()`/`getLabHistory()` read from, used by both bulk-copy functions and the sidebar) is only populated once at app boot (`app-state.mjs` → `hydrateClinicalRepoIntoReadModel`). Prevention: when two different in-memory stores exist for the "same" data (legacy array vs. read-model cache), grep every write path for both before trusting that "the UI looks right" means the data is fresh everywhere — a read-model that's fed only at boot is a silent trap for any feature added later that reads from it. Fixed by applying the already-known-correct local snapshot to `_cache` after persist succeeds (`_applyRepoSnapshot(snapshot, ...)` in `clinical-repo-persist.mjs`), without touching the deliberate `echoSnapshot: false` IPC behavior.

Root cause: `:has-text()` with no scoping matches the first DOM-order element containing that text anywhere on the page, not the visually-obvious one — a settings-dropdown entry or similar can share label text with the actual navigation tab and win the match.
Prevention: When a verify-tool screenshot looks wrong, check whether the intended UI state actually changed (dump DOM/URL/active-tab state) before concluding the app is broken. For this app's own tab/screen navigation, prefer `page.evaluate(() => document.getElementById('apptab-lab')?.click())` against real DOM ids from `public/partials/layout/app-body.html` over the text-locator helpers.
