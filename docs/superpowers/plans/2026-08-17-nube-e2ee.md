# Nube end-to-end encryption (E2EE) — implementation plan

## Context

Nube (cloud sync) sends clinical data to a personal Cloudflare account as plain, readable JSON. `docs/core/15-security.md` already documents this gap and forbids claiming Nube is encrypted until "envelope DEKs" ship. The user believed this was already done — it is not. This plan scopes the real fix: the client encrypts before sending, Cloudflare only ever stores unreadable ciphertext, and only enrolled devices can read the data.

Two things currently force the server to read plaintext:
1. **Merge (last-write-wins)** — `cloud/sync-worker/src/lww.js` compares `updatedAt` + `actorId` per field path.
2. **Interno phone board** — `cloud/sync-worker/src/interno/board.js` reads patient names + team/guardia data to build a board for phones.

Finding from research: LWW only needs `path`, `updatedAt`, `actorId`, and a revision number — never the actual field **value**. So merge can keep working server-side without ever seeing plaintext, as long as we encrypt values but leave that metadata alone. Interno is the real blocker, because it needs to show a patient name. Decision made: **Interno switches to bed number + short alias**, so it no longer needs any PHI field. That removes the second blocker and makes full E2EE possible.

## Design

**Key:** one AES-256-GCM room key ("DEK"), generated on the device that creates the room.
**Wrapping:** DEK is wrapped (encrypted) with a key derived from the user's Nube password via PBKDF2 (Web Crypto `subtle.deriveKey`, matches the hashing primitive the Worker already uses in `password.js`). The wrapped DEK is stored server-side per room. Any device that logs into that room with the correct password can unwrap the DEK locally. Cloudflare stores the wrapped blob but never holds the unwrapped key.
**What gets encrypted:** the `value` of every field in a sync op (census names, diagnoses, notes, indicaciones, labs, vitals, todos, agenda). AES-GCM with a random IV per field.
**What stays plaintext (needed for merge/routing):** `path`, `updatedAt`, `actorId`, `revision`, room id, session tokens. These are structural metadata, not clinical content.
**Interno:** the client computes a separate, small "board summary" (bed + alias + guardia assignment only, no name) and sends that unencrypted, as its own object — not part of the encrypted room state. This is the only thing Cloudflare/Interno phones ever see in the clear.

## Files to change

**New client module**
- `public/js/features/cloud-sync/crypto.mjs` — new. AES-256-GCM encrypt/decrypt per field value, PBKDF2 key derivation, DEK generate/wrap/unwrap, all via `window.crypto.subtle` (browser-native, no new dependency).
- `public/js/features/cloud-sync/crypto.test.mjs` — new, follows existing colocated test pattern (`node:test`, mocked `globalThis.crypto`).

**Integration points (encrypt outgoing / decrypt incoming)**
- `public/js/features/cloud-sync/api-client.mjs:57` — encrypt op values before `JSON.stringify`/push.
- `public/js/features/cloud-sync/api-client.mjs:60` — decrypt op values after `res.json()`/pull.
- `public/js/features/cloud-sync/cloud-push-direct.mjs:102-106` — pass DEK through the push call.
- `public/js/features/cloud-sync/settings.mjs` — add storage for the wrapped DEK (mirrors existing `ROOM_ID_KEY`/`TOKEN_KEY` pattern).
- `public/js/features/cloud-sync/panel-conexion-bootstrap.mjs` — on room create: generate + wrap DEK. On room join: fetch wrapped DEK, unwrap with password.

**Interno board (bed/alias only)**
- `cloud/sync-worker/src/interno/board.js` — stop reading `entries[].nombre`; read a new unencrypted `internoBoard` field (bed + alias + guardia) instead of the full snapshot.
- Client side (wherever the board summary is generated before push — inside `cloud-push-direct.mjs` or a new small helper) — build the alias (e.g. "Cama 12" or a short non-identifying tag) and push it as its own unencrypted field alongside the encrypted room state.

**Server (mostly unchanged — dumb relay)**
- `cloud/sync-worker/src/lww.js` — no logic change; already only touches path/updatedAt/actorId.
- `cloud/sync-worker/src/crypto-at-rest.js` — remove the legacy `WORKER_DATA_KEY` AES path once client E2EE ships (dead code, no longer the encryption layer).
- `cloud/sync-worker/schema/` — no new migration needed; `ciphertext`/`iv` columns already exist, just start populating them for real (values are already ciphertext strings from the client; server stores as-is).

**Docs**
- `docs/core/15-security.md` — update once shipped: remove the "do not claim encrypted" warning, document the new model.

## What this does NOT cover (explicitly out of scope for this plan)

- Rotating the DEK when a team member leaves (revoke access) — needs a follow-up design.
- Multi-key-per-member (asymmetric invite) — v1 uses one shared password-derived key per room, simplest and matches how rooms work today.
- Recuérdame token still stored in plaintext on disk (`0600` file) — separate known gap, not this plan.
- Server-side search/filter features that would need to read plaintext — none currently exist, but any future feature idea must respect that the server cannot read field values anymore.
