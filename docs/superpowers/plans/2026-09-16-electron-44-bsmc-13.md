# Plan: upgrade Electron 41→44 and better-sqlite3-multiple-ciphers 12→13

## Goal

Move R+ to Electron 44.x and better-sqlite3-multiple-ciphers 13.x with zero risk to the encrypted patient DB and zero broken installs, using a staged, rollback-safe order.

### How the native DB binary gets built (this is the coupling)

- `scripts/fetch-sqlite-electron.mjs:32-51` downloads a prebuilt `.node` from GitHub release `m4heshd/better-sqlite3-multiple-ciphers` by exact asset name `better-sqlite3-multiple-ciphers-v<bsmcVersion>-electron-v<ABI>-<platform>-<arch>.tar.gz`. ABI comes from `node-abi.getAbi(electronVersion)`.
- Fallback: `scripts/rebuild-native-db.mjs:21-29` runs `npx @electron/rebuild -f -w better-sqlite3-multiple-ciphers` (source compile; needs Xcode CLT + Electron headers).
- Release path: `scripts/electron-builder-before-pack.cjs` fetches the prebuild per target arch (arm64, x64, win32-x64); `after-pack.cjs` restores host arch. `npmRebuild: false` in `package.json:81`.
- Tests run under Electron's Node (`scripts/run-with-electron-node.mjs`, `ELECTRON_RUN_AS_NODE=1`), so tests and app share one ABI.

So: **a prebuild must exist on GitHub for the pair (bsmc version × Electron ABI)** for all three targets, or the build falls back to source compile. Bumping Electron changes the ABI; bumping bsmc changes the version. Both change the asset name. The two upgrades are one decision with two knobs.

### How the DB is encrypted

- `lib/db/db-manager-auth-internals.mjs:100`: `conn.pragma(\`key = "x'${keyHex}'"\`)` then WAL + foreign_keys. Rekey at `db-manager-auth-unlock-flows.mjs:406`.
- **No `cipher` pragma is set anywhere in `lib/`.** The on-disk format is whatever cipher the library compiles in as default. If 13.x ships a newer SQLite3MultipleCiphers with a changed default or changed KDF/page defaults, existing DBs will fail to open with "file is not a database". This is the single most important thing to verify.
- Boot gate: `main.js:996-1008` calls `loadNativeDatabase()`; on failure shows error box and quits. `lib/native-runtime-probe.js` gives the user-facing ABI-mismatch message.

## 1. What can break: Electron 41→44

Ordered by probability × damage.

1. **Native ABI mismatch (certain, blocks boot).** ABI 145→149. The installed `better_sqlite3.node` will not load. `main.js:1005` shows "R+ no pudo iniciar". Mitigation is the prebuild fetch/rebuild above. `@electron/rebuild 3.7.2` depends on `node-abi ^3.45.0` (resolved 3.96.0, which knows 44) — OK, re-check after `npm install`.
2. **Prebuild not published for bsmc 12.10.0 × ABI 149.** 12.10.0 predates Electron 44. If the asset is missing, `beforePack` throws and the release build fails; dev falls back to source compile (slow, needs toolchain, and Windows x64 cross-fetch has no fallback at all). This is why Electron cannot be bumped alone to 44 unless 12.10.0 has a 149 asset. Verify with one HTTP HEAD before anything.
3. **electron-builder support for Electron 44.** Installed 26.15.3 — check release notes for the Electron 44 framework layout; the Mac notarize/hardenedRuntime path (`package.json:87-112`) and `lib/mac-quiet-swap.mjs` both depend on the `.app` layout not changing. Bump `electron-builder` and `electron-updater` to latest in the same PR; they move together.
4. **Renderer security defaults.** Already `nodeIntegration: false`, `contextIsolation: true`, preload only, no `webview`, no `@electron/remote`, no `--no-sandbox` (`main.js:232-244`). Sandbox default-on since Electron 20. Low risk.
5. **APIs in use are modern already:** `protocol.handle` + `net.fetch`, `setWindowOpenHandler`, `safeStorage`, `session.webRequest.*`, `dialog`, `clipboard`, `Menu`, `shell.trashItem`, `app.requestSingleInstanceLock`. Nothing legacy (`registerFileProtocol`, `BrowserView`, `remote`) present. Still grep each against Electron's 42/43/44 breaking-changes pages.
6. **macOS minimum version.** Electron 44 may raise the floor above 41's. The hospital fleet may include old Intel Macs. If the floor rises, install on an old Mac silently fails to launch, and the in-app downgrade cannot help because it never starts.
7. **Node version inside Electron.** Low risk to `ws`, `pdf-parse`, `jszip`, `pdf-lib` (pure JS). `run-with-electron-node.mjs` test-runner flags stay valid.
8. **Code signing / notarization drift.** No config change expected, but a new Electron.framework means a fresh notarization pass.
9. **Chromium rendering changes.** Custom UI (teal workbench); three Chromium majors can shift fonts, scroll, `printToPDF` output, form controls. Not a boot risk, but the .docx/PDF pipeline and printing need eyeballing.
10. **Self-update chain.** Squirrel.Mac/NSIS and the in-app downgrade (`stable-versions.json`) don't care about Electron version. The DB file is the only thing that must survive both directions.

## 2. What can break: better-sqlite3-multiple-ciphers 12→13

1. **On-disk cipher compatibility (the real risk).** No `cipher`/`kdf_iter`/`cipher_page_size` pragma is pinned, so the DB depends on the library default. If 13.x changed that default, every existing install fails to unlock, and rollback via `stable-versions.json` only works if 13.x didn't rewrite the header. Must be proven by a two-way file test, not by reading the changelog.
2. **JS API surface.** App uses only `new Database(path)`, `.pragma`, `.prepare/.run/.get/.all`, `.exec`, `.transaction`, `.close`, `.open`. No `backup|serialize|function|aggregate|loadExtension|safeIntegers|SqliteError` usage found. A break in `pragma()` return shape or `Database` constructor options would matter — read the v13.0.0 release notes for that.
3. **Prebuild matrix.** 13.0.3 must publish assets for ABI 149 on `darwin-arm64`, `darwin-x64`, `win32-x64`. Dropped `darwin-x64` prebuilds would break the Intel DMG silently (cross-arch load probe is skipped).
4. **Node engine.** Irrelevant for Electron 44 (its Node is newer); relevant only if tests ever run under system Node (they should not — `test:one` uses Electron's Node).
5. **Config touch points carrying the version string:** `package.json:54` (dependency), `package.json:168` (`allowScripts` key is version-suffixed — must change to `@13.0.3` or the install script is blocked and no `.node` is built).

**Coupling, stated once:** the asset name is `v<bsmc>-electron-v<ABI>`. Bumping only Electron needs `12.10.0 × 149`; bumping only bsmc needs `13.0.3 × 145`; bumping both needs `13.0.3 × 149`. Only the pairs that exist on the GitHub release page are buildable. Check all three pairs with HEAD requests before choosing the order.

## 3. Safeguards before either upgrade

**A. Rollback plan.**
- 8.3.8 stays `recommended: true` in `stable-versions.json` until the new build is verified live for one clinic day. Do not flip `recommended` in the same release commit.
- First upgraded release is a normal semver bump (8.4.0), so `allowDowngrade` + the stable list can return users to 8.3.8.
- The DB file must open under both 8.3.8 (bsmc 12.10.0) and 8.4.0 (bsmc 13.0.3), proven by safeguard B. If it does not, the upgrade is blocked, not patched.
- Keep the gitignored native cache from the 41/12.10.0 world untouched so the dev tree can be restored in seconds.

**B. Two-way DB round-trip test (new, one test file).**
On a branch with the new versions, a `node:test` file under `lib/db/` that:
1. Creates a temp DB with `openTestDb(TEST_KEY_HEX)`, writes one synthetic patient row, closes.
2. Reopens it, reads it back, runs `applyMigrations`, rekeys (`pragma rekey`), reopens with the new key.
3. Asserts `pragma cipher` (or equivalent) reports the same cipher name and same `kdf_iter`/`cipher_page_size` as a fixture recorded under 12.10.0.
Plus one manual cross-version check (cannot be automated in-repo): copy a synthetic DB file created by the 8.3.8 dev tree into the branch userData dir, unlock via the app, copy it back to an 8.3.8 tree and unlock again. Never use a real clinical DB — use the `export:demo-patients` fixtures.

**C. Existing gates to run, in order:** `npm run rebuild:db-native` (strict) → `npm run test:one -- lib/db/db-manager.test.mjs` → `test:one` on `lib/db/schema.test.mjs`, `migrate-from-legacy.test.mjs`, `ipc-handlers.test.mjs`, `main-update-feed.test.mjs` → `node scripts/verify-release-natives.mjs` → `npm run metrics:check`.

**D. Manual smoke in the running (packaged) app, per arch:**
1. Cold boot, unlock with passphrase, open a patient, add a lab, generate `.docx`, print preview.
2. Lock, quit, relaunch, unlock again (WAL checkpoint survived).
3. Cambiar contraseña (rekey) then relaunch + unlock.
4. Nube: connect, push one op, pull. LAN: one peer discovery.
5. Ajustes → Versiones estables → downgrade to 8.3.8 → unlock same DB → upgrade again.
6. Intel Mac (or Rosetta) launch of the x64 DMG; Windows x64 NSIS install + unlock.
7. Confirm `window.electronAPI.dbStatus()` returns `sqlcipherReady:true, nativeReady:true`.

**E. Staged order — Electron first, then bsmc, not together.** Two variables in one commit cannot be bisected. Practical order is decided by which (bsmc × ABI) pair actually has a published prebuild — check with HEAD requests before starting.

**F. Straight to 44, one intermediate stop (43) only if 44 fails a gate.** Read Electron's 42/43/44 breaking-changes pages in one sitting (cumulative).

## 4. Recommended sequence

**Option A (recommended): three small steps, three commits, one release.** Step 0 hygiene, Step 1 whichever of bsmc/Electron has a published prebuild, Step 2 the other, then one 8.4.0 release with 8.3.8 kept as recommended stable for a week. Safe to bisect.

**Option B: both bumps in one commit.** Faster by half a session. Loses the ability to tell which bump broke the DB or the boot. Not recommended for a module that guards patient data.

**Go with A.**
